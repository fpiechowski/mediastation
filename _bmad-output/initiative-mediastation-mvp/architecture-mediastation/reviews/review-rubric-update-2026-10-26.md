# Review: update spine'u 2026-10-26 (epic-home-screen)

Maszyna: review powstał na **UM760** (`MEDIASTATION` / `F7BSI` / `EliteMini Series`).

**Werdykt:** delta usuwa Source conflict z Notes epiki: Actions idą do Shell w trybie `shell`, AppMenu należy do Shell, nie ma Intentu otwierającego menu. Jest zgodna z R1–R8 i z decyzjami z 2026-10-26. Przed puszczeniem pętli bez nadzoru trzeba jednak poprawić dwie reguły. Pierwsza to eksport schematów przez `dotnet test` wołany z `npm`. Wprowadza zagnieżdżony build tego samego projektu testów w jednym przebiegu buildu solucji. Do tego nie gwarantuje odświeżenia typów przy Application Control, a przy blokadzie zabiera jedyne dotychczasowe obejście. Druga to dostarczanie `action` „każda dokładnie raz”. Bez granicy taka reguła po zawieszeniu UI odtwarza zaległe naciśnięcia, a przed `ready` nie da się jej spełnić. Do tego dochodzą trzy luki średniej wagi, w których dwie stories mogą zbudować rzeczy niezgodne ze sobą.

Ikony w `config/icons/` z fallbackiem i `warn` (Decision 2026-10-26, story 5) są w AD-11. R7 (puste `title`/`icon`) jest w AD-11. Vitest w `web/` (story 3) jest w AD-13 i Stack.
- **Kod:** `MessageTypes` nazywa `Action`/`LaunchApp`/`RestartApp`/`CloseApp` jako `action`/`launchApp`/`restartApp`/`closeApp`, zgodnie z tabelą mostu. `ShellBridge` odrzuca dziś wszystko poza `ready` z `bridgeMessageRejected`, więc tabela rozszerza ten wzorzec. `ConfigValidation` już odrzuca `appMenu` w `input.json`. `InputPolicy` emituje `press` OK dopiero na key-up przed progiem (AD-8 l. 202), więc long-press na `Background` nie wyśle wcześniej `LaunchApp`. ## Szczegóły

### H1 — eksport schematów z `npm` przez `dotnet test`

Łańcuch po zmianie: `dotnet build MediaStation.slnx` → (równolegle) `MediaStation.Core.Tests` oraz `MediaStation.App` → `BeforeBuild`/`BuildWeb` → `npm run build` → `npm run contracts` → `dotnet test tests/MediaStation.Core.Tests` → drugi, niezależny build `MediaStation.Core.Tests` i `MediaStation.Core` (ta sama konfiguracja Debug, te same katalogi wyjściowe). Dwa procesy MSBuild nie koordynują zapisu do `obj/`. Dzisiejszy `BuildWeb` unika tego, bo eksporter buduje taskiem `<MSBuild>` w tym samym węźle. Reguła „`npm run build` i target `BuildWeb` w App wołają tylko npm” wprost wyklucza ten mechanizm. Pętla bez nadzoru uruchamia `dotnet test` w każdej story, więc flaky build trafi do niej jako fałszywy błąd.

Druga warstwa: memlog przyznaje, że zysk to „brak dodatkowego obrazu”, a nie odporność na Application Control. Dawniej przy blokadzie `SchemaExport.dll` działało `npm run build` + `-p:SkipWebBuild=true` (acceptance-3 P0.2). Po zmianie `npm run build` sam uruchamia hosta testów, więc przy jego blokadzie nie ma żadnej drogi do `shell/`. Spine powinien to nazwać i powiedzieć, co wtedy robi odbiór na UM760.

### H2 — `action` „każda dokładnie raz”

Kolejka snapshotów jest latest-wins właśnie po to, żeby zawieszony UI nie wpływał na core (AD-14). Actions z definicji nie mogą być latest-wins. Bez granicy wieku albo rozmiaru zaległe naciśnięcia wykonają się jednak po odwieszeniu, a tego żaden użytkownik pilota nie chce. AD-10 rozwiązuje ten sam problem dla strony („`action` do strony są odrzucane, a nie buforowane”). Shell powinien dostać tę samą zasadę i nazwane zdarzenie logu, żeby test i odbiór mogły ją sprawdzić.

### M2(b) — kanał Action z Orchestratora

`OrchestratorResult(commands, snapshot)` nie ma dziś miejsca na „wiadomość do Shell”. Jeśli story 3 zrobi z tego Command, AD-4 każe mu nadać `cmdId` i czekać na `CommandCompleted`/`CommandFailed`. To sprzeczne z payloadem „rekord `Action`” na moście i z fire-and-forget. Wystarczy jedno zdanie w AD-8 albo AD-16.
